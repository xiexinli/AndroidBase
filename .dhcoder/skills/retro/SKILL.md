# Retro

回顾的是**AI 辅助开发环境与工作流程**，不是产品/团队业务复盘。目标是找出可证实、可重复的问题，并提出少量高价值改进；不为每次任务制造仪式，也不为凑建议而找问题。

## 何时运行

- 用户明确要求复盘、retro，或希望改进 Agent 工作方式。
- 较大开发/排障/评审任务中出现了明显且可复用的摩擦，例如规则缺失或互相冲突、导航困难、验证环缺口、反复误解、工具链阻塞。
- 相同问题跨任务重复出现，值得调整项目级配置。

简单问答、只读检查、小型顺利完成的改动不运行本技能。若长任务结束时只有轻微、一次性的障碍，不必单独做 retro；只需在正常收尾中简述即可。

## 复盘步骤

1. **确定范围**：针对一个刚完成的任务或用户指出的摩擦，不泛化为整个项目审计。
2. **收集证据**：查看本次对话中可观察到的失败、返工、遗漏、重复步骤、验证结果与用户纠正；必要时只读检查直接相关的 Agent 配置。区分事实与推测，不臆测其他会话或团队体验。
3. **找根因**：判断问题属于仓库事实/导航、规则、技能路由、验证反馈、工具、权限，还是需求不清；先查现有资产，避免建议重复能力。
4. **按价值排序**：仅输出有证据且可采取行动的建议。优先降低反复返工、误改或验证失败的风险；不以新增文件/规则数量衡量改进。
5. **提出最小改动**：每项建议说明观察到的证据、可能根因、建议改什么（具体文件/位置）、预期收益和代价/风险。一次性问题优先用局部流程修正，不急于沉淀永久规则。
6. **征求确认**：只提供建议，不自动编辑 `AGENTS.md`、规则、技能、构建配置或脚本。若用户批准，再按项目任务分级实施、验证并汇报。

## 输出格式

### 观察
- 事实与证据；没有明显问题时明确说“本次未发现值得固化的流程问题”。

### 建议（按优先级）
每项包括：问题/证据 → 最小改动位置 → 预期收益 → 风险或成本。没有建议就不造建议。

结尾给出明确推荐，以及是否需要用户批准实施。保持精简，不复述整个任务，也不评价个人表现。
