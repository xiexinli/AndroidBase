# Domain Modeling

在需求与代码设计过程中主动澄清领域模型。重点是及时识别含混术语、用具体场景验证概念边界，并把已确认的信息记录到合适文档；不要把推测写成事实。

## 项目文档位置

- 领域语言与概念关系：优先维护仓库根目录 `CONTEXT.md`；如未来确有彼此独立的业务上下文，再讨论分拆和索引，勿预先造目录。
- 架构决策：使用 `docs/adr/NNNN-short-title.md`，编号递增；目录在首个 ADR 需要时再创建。
- 既有格式：沿用 `.dhcoder/skills/grill-with-docs/CONTEXT-FORMAT.md` 和 `ADR-FORMAT.md`。不要另造 GLOSSARY 文件或平行 ADR 格式。
- `CONTEXT.md` 只记录项目特有的领域术语、关系、示例和已解决的歧义；不放实现细节、技术规范或未决事项清单。

## 工作方式

1. **挑战含混词语**：指出一词多义、同义词泛滥或与 `CONTEXT.md` 冲突之处，提出精确候选词并向用户确认，不擅自定义业务事实。
2. **用场景检验边界**：针对正常路径、边界情况、失败/取消/重试等提出具体问题，厘清实体、状态和关系。
3. **对照代码与文档**：用户描述与实现、测试或既有决策不一致时，明确列出证据和冲突，请用户决定哪方代表当前规则。
4. **即时沉淀**：术语或关系确认后，及时更新 `CONTEXT.md`；未经确认的内容标为问题，不写成定论。定义简洁，只纳入项目领域特有概念。
5. **谨慎记录 ADR**：只有同时满足以下条件才建议记录：决策不易逆转、缺少背景会让后来者困惑、并且确实是在多个方案间权衡后的选择。ADR 写明背景、决策和理由即可；简单或显而易见的选择不记。

## AndroidBase 约束

- 领域术语不改变既定模块责任：`:base/domain` 保持纯 Kotlin；页面与导航留在宿主 `:app` / `:demo`；数据访问由 data 层承担。详细约束以 `AGENTS.md` 与 `.dhcoder/rules/architecture.md` 为准。
- 不因领域模型讨论就预先新增抽象、模块或技术；先解决语义，再由 Spec/架构流程决定实现。
- 对项目已有术语和技术名（如 `ApiResult`、Repository、UseCase）保持原样，不为套用通用词汇而重命名代码。

## 收尾

说明哪些术语/关系已确认、哪些仍待确认，列出更新的文档；若没有形成稳定结论，不要为了“留下产物”而创建空文件。
