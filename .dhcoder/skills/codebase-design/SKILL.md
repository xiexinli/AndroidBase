# Codebase Design

目标是让调用者通过清晰且尽可能小的接口获得足够能力，并让实现细节与变化集中在合适的位置。把这些原则作为设计工具，不把它们当作必须新增抽象的教条。

## 词汇

- **模块（module）**：有可辨识接口与实现的代码单元，可以是函数、类、package 或跨层功能切片。
- **接口（interface）**：调用者为正确使用模块必须了解的内容，包括类型、前置条件、顺序、错误语义、配置和重要性能特征；不限于 Kotlin `interface` 关键字。
- **深度（depth）**：接口提供的能力相对于调用者必须理解的复杂度。深模块以简单接口隐藏有价值的复杂实现；浅模块则接口复杂但只做转发。
- **接缝（seam）**：可以在不改调用位置的情况下替换实现行为的位置；在 Kotlin/Android 中可能是构造注入的接口、函数参数或模块公开入口。
- **适配器（adapter）**：在接缝处承接具体技术实现的部分，例如 Retrofit/Room 的数据实现或测试替身。
- **局部性（locality）**：修改、知识和验证集中在少数实现位置的程度；**杠杆（leverage）**：调用者通过接口获得的能力。

## 设计检查

1. **先界定候选与调用者**：基于代码证据说明当前模块、依赖方向、调用者和变化点；架构扫描技能用于发现候选，本技能负责推敲选中候选的设计。
2. **比较至少两个方案**：明确接口表面、隐藏的复杂度、错误/状态行为、依赖归属、调用示例、可测试性、迁移范围与取舍；必要时才请求并行独立方案。推荐一个方案并说明原因。
3. **检查深度与局部性**：是否能减少重复编排、让变化集中在一处？删除该模块后复杂度是消失了，还是散落到多个调用者？避免把单纯转发包装误判成有价值的模块。
4. **把接口作为主要测试面**：测试可观察行为与契约，而非私有实现细节。内部测试缝隙可以存在，但不应仅为测试而泄露到公开接口。
5. **依赖注入要有理由**：依赖由外部提供通常更易测；但不要为了假想替换而制造端口。只有确有多个合理实现（例如生产实现与有价值的测试替身，或真实运行时变体）时，抽象接缝才可能值得维护。
6. **返回值与副作用**：可将确定性计算与 I/O 分开；对副作用边界采用显式依赖和可验证结果。不要机械要求所有副作用都改造成纯函数。

## AndroidBase 适配规则

- 不改变 `:app` / `:demo` → `:base/domain`、`:base/data` → `:base/domain` 的项目依赖方向；domain 不依赖 Android 框架。最终以 `AGENTS.md` 和 `.dhcoder/rules/architecture.md` 为准。
- Hilt 是既定 DI；如需接缝，使用项目现有的构造注入和 Hilt 绑定方式，不引入第二套容器。
- 网络与缓存继续遵循现有 `ApiResult`、Repository、Room 回退等约定；不设计绕过统一网络/数据路径的并行入口。
- Kotlin `interface` 是一种实现手段，不等同于所有模块都必须声明接口。若只有一个实现且没有真实替换/边界需求，优先保留简单实现。
- 不凭抽象原则自动合并或拆分模块；先展示代码证据、方案与风险，按现有任务分级取得必要确认。

## 何时使用

- 用户要求优化接口、模块职责、可测试性或 AI 导航性。
- `improve-codebase-architecture` 已识别并经用户选定一个深化候选。
- 其他技能遇到重要接口设计问题时可引用本技能词汇与检查项，不必重复加载整个仓库。

## 输出

用简明对比表或要点给出推荐方案、接口示例、依赖/测试策略、受影响调用者、迁移与验证计划。只给设计时不修改代码；用户授权实施后按项目 Spec/计划/验证流程执行。
