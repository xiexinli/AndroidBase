# App Grill PM

## Overview

这是实现前的需求与设计澄清技能：把 PRD 或用户输入整理为经用户确认的产品行为和设计摘要，作为当前调用的交付结果。

形成交付结果前，影响产品实现或验收的问题需要闭合，设计需要得到明确批准。

职责范围是完成产品澄清并输出设计摘要。`APPROVE_DESIGN` 确认本 Skill 的设计交付。

## When to Use

- 输入是 PRD、功能描述或用户直接提出的 App/产品行为变化。
- 需求包含用户流程、交互、状态、分支、异常兜底、兼容范围、验收或配套物料，但仍有解释空间。
- 需要在实现前统一产品语义和设计方向。

输入只要求文档摘要、格式转换、代码影响分析，或已具备可直接实施的明确行为约束时，无需使用本技能。

## 1. 输入门槛与事实收集

输入需明确“在哪里/作用对象、修改什么、从什么行为变为什么行为”。输入仅包含“优化”“调整”或模块大类时，先补充具体需求，再开始设计或实现。

- 直接读取粘贴文本、用户描述或 Markdown。非 Markdown 文档先取得可靠文本；图片、附件或视觉信息可能影响行为而未可靠提取时，列为资料缺口并等待确认后再设计相关部分。
- 飞书链接通过已授权的飞书 MCP 或 CLI 读取；读取受阻时请用户提供可阅读文档，并保持 OAuth、scope、权限和分享设置不变。
- 读取目标项目 `AGENTS.md`、Wiki 索引和与需求直接相关的 Wiki/代码，只扩展到能解释需求变化的范围。
- 代码/Wiki 提供现状证据；基于这些证据的推断需标注为“AI 基于当前实现或 Wiki 证据的推断，需与开发人员确认”。

## 2. 先分类路径

先说明当前路径；在不确定时选择较重路径。

- **Spike**：聚焦可行性问题。先说明探查问题和范围，获得用户同意后调查，交付建议并标记探查产物的临时性质。
- **Bounded**：已有流程的小范围变化。逐题澄清，在对话中给出简短设计，等待用户明确批准。
- **Architectural**：新系统、新子系统或跨模块变化。逐题澄清，比较 2–3 个设计方向，分段确认设计后输出摘要。

发现隐藏复杂度时升级路径。三条路径均在设计获明确批准后进入实现阶段。

## 3. 全量功能点盘点

进入逐题澄清前，一次输出输入中的全部功能点，按出现顺序编号：

```markdown
### 功能点 N：<页面或功能>

AI 语义解析：
- 作用对象/入口：
- 触发条件：
- 当前行为：
- 目标行为：
- 状态、分支与优先级：
- 保持不变：
- 验收边界：

语义已完整：
- <已闭合规则>

需要澄清：
- <只列主题，不在盘点阶段展开问题>
```

盘点消息仅包含功能点盘点。末尾列出问询顺序并请用户回复“继续”；“继续”确认进入下一阶段。用户修正解析时，更新受影响内容和顺序后再次等待“继续”。

## 4. 一次性集中确认全部物料

收到盘点后的“继续”后，集中确认全部已识别物料的状态。基于需求和必要的代码/Wiki 现状，识别分流信息、埋点文档、设计稿、站点范围、多语言文档，以及按需识别的接口契约、登录态、权限、第三方能力、合规和兼容说明。

使用一个总问题和一张表，要求用户为每项一次性选择 `已提供`、`后补` 或 `不需要`：

```markdown
本次需求涉及以下物料，请一次确认每项状态；本次只确认状态，不审查物料内容。

| 物料 | 识别原因 | 状态：已提供 / 后补 / 不需要 |
|---|---|---|
| <物料> | <影响的功能或设计> | <待确认> |
```

`后补` 和 `不需要` 记录为已完成的产品决策。所有物料行完成状态确认后，进入普通需求/设计问题；未回答的行保留在原表中补全。用户可观察兜底需覆盖意外同时配置、资源缺失、类型错误或无效组合。接口字段名、数据类型和路径属于开发协作细节；接口缺失或失败时的用户行为仍需澄清。

## 5. 单题需求与设计澄清

阅读 [需求与设计澄清检查清单](references/prd-review-checklist.md) 和 [提问模式](references/question-patterns.md)。物料总问题完成后，按功能点顺序每轮确认一个会改变实现或验收的问题，覆盖：

- 显示/隐藏、入口、点击、跳转、返回、刷新和状态恢复；
- 多场景进入条件、互斥关系、同时命中优先级、默认行为；
- 数据缺失、异常输入、接口失败、误配置的兜底；
- 站点、语言、账号、版本、分流和兼容范围；
- 最大行数、截断、展开/收起、动效是否执行等用户可观察规则；
- 当前实现、Wiki 与需求输入冲突时的目标业务口径。

已闭合的内容同步确认即可。存在多个规则时，列出客观选项、适用条件和影响，并保留“其他”。代码/Wiki 推导的问题附开发确认提示。本环节聚焦影响行为与验收的规则，OKR、CTR、字号、间距、颜色数值和动效时长等非行为细节留给相应设计交付物。

## 6. 设计摘要与批准

全部影响实现或验收的问题闭合后，输出：

- 澄清需求：功能点最终语义、状态/分支、范围、保持不变和物料状态；
- 设计摘要：用户流程、交互、异常行为、兼容边界、验收标准和回归范围；
- 未决问题和剩余风险：为空时完成交接；存在时明确列出并等待闭合。

Bounded 路径给出简短设计；Architectural 路径先给 2–3 个设计方向及取舍，再分段确认。用户明确 `APPROVE_DESIGN` 后，输出已确认的澄清需求和设计摘要。

## 7. 产出与恢复条件

- 交付物：经确认的澄清需求和设计摘要，包含功能点最终语义、状态/分支、范围、保持不变、物料状态、用户流程、异常行为、兼容边界、验收标准和回归范围。
- 交付位置：将交付物保留在当前对话，供用户直接审阅和采用。
- 恢复条件：输入不可读、媒体资料未确认、现状证据冲突、物料状态未全答或产品问题未闭合时，说明资料缺口、已尝试动作和恢复条件；条件满足后继续澄清。

## 执行校准

- 对完整 PRD 仍完成全量功能点盘点；已完整的内容在盘点中标为已闭合。
- 盘点完成并收到“继续”后，再发送唯一的物料总问题。
- 在设计获得明确批准后，进入行为变更实现。
- 在一张物料表中集中确认全部识别物料。
- “继续”用于进入澄清循环；`APPROVE_DESIGN` 用于批准设计。
- 代码和 Wiki 作为现状证据，目标业务口径由 PM 确认。
